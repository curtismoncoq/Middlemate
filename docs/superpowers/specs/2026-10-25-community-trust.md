# Community trust and shared persistence

Approved scope: independent user reputation, observed technical reliability, and MET Norway concordance. Weather disagreement and votes never automatically slash. Existing LLM scoring and enforcement remain unchanged. Stakes and actual sanctions stay on the existing Stellar registries without ABI changes.

Supabase Postgres stores paid call receipts, reviews, reports, provider replies, moderation decisions, login challenges/sessions and audits. All tables have RLS enabled with browser access revoked; the application backend authorizes every operation using a wallet signature (SEP-53), a single-use expiring challenge and an HttpOnly session. Every row belongs to a shared deployment namespace. The Supabase server key never enters browser bundles.

The invocation gateway observes the selected listing's actual request and settlement, then independently verifies the successful USDC transfer on Stellar before recording buyer/provider/price/listing identity. Transfers alone cannot identify one of several services sharing a wallet; old unbound payments do not grant review rights. Request/response bodies are not persisted. A failed persistence write is surfaced without retrying or charging the call again.

One editable review per wallet/listing, backed by a successful non-audit paid call. An update needs a newer call; self-review is prohibited. Red votes require a reason. Reviews and provider replies are public, reports and their private descriptions are visible only to buyer, provider and moderators. Reports reference an actual paid call. Public decisions disclose the reason and chain transaction links without the private report body.

Providers see their reviews, incoming reports, response deadline and comparisons. Buyers see exact listing call history, review/report actions and case progress. Votes cannot initiate sanctions. Configured moderator wallets review cases; they cannot adjudicate their own provider/buyer cases. Financial sanctions require either provider response or expiry of the stated response period, a motivated decision and an additional wallet-signed confirmation. The server auditor key executes slash then pause. Each chain result is persisted immediately; failed pause may be retried without repeating a recorded slash.

Limits: one wallet is not one person; paid access only raises Sybil cost. Observed response success is not an uptime SLA. An HTTP outcome is observed by the gateway, while payment is confirmed onchain. Moderator judgment is centralized for this hackathon. Postgres and Stellar cannot commit atomically; crash recovery may require reviewing a chain tx. A 10-second registry exit cannot guarantee stake availability through a longer moderation process. Database credentials are required for community actions; existing payment/listing paths continue without community configuration.
